# 多 agent 调研：怎么拆、怎么跑、跑完怎么收

## 1. `ctx`：所有 agent 共享的固定事实

写成多行文本，越具体越好，agent 才不会瞎排：
```
【固定事实，不可改动】
- 出行 2 人，从杭州来，爱吃、爱人文，追求性价比；地铁和打车一半一半都行。
- 去程：10/1（周四）G38 07:47 杭州东 → 08:56 南京南。
- 酒店：XX酒店（XX店），XX路XX号；离XX地铁站 350m；14:00 后入住、12:00 前退房；前台可寄存行李。
- 回程：10/2（周五）G235 19:00 南京南 → 20:01 杭州东，已改签过不能再改（建议 18:15 前到站）。
- 用户已有的想法/草案（可推翻但要给理由）：……
- 这是国庆黄金周，人流是最大变量；能找到的经验多是去年的，请标明年份。
- 节奏：每天 3–4 个核心点，步行 ≤10km。
```

## 2. `topics`：怎么拆（6–8 路，按「时段」和「主题」交叉切）

上次南京用的 7 路，基本可以照搬：

| key | 负责什么 |
|---|---|
| `day1-daytime` | 到站 → 酒店寄存 → 第一天白天的景点比较（预约规则/放票时间/现在还能不能约/开放时间/时长/人流实帖）+ 下午 2–3 个同级备选及触发条件 |
| `day1-night` | 夜游核心区（是否预约/限流/单向通行/地铁跳站）、游船（购票渠道/排队/码头）、替代夜游、往返交通 |
| `dayN-xxx` | 最后一天：重点景区 + 景区内交通 + 「最晚几点必须往车站走」+ 车站进站排队/寄存 |
| `food-<片区A>` | 酒店周边 + 夜游片区：每区 4–6 家（必点/人均/理由/排队/避雷）+ 当地必吃清单各推 1–2 家 |
| `food-<片区B>` | 其余片区 + 景区周边（现实点：景区周边常常没什么好吃的）+ 车站 + 伴手礼（能不能带上高铁） |
| `xiaohongshu-browser` | **唯一能用 Chrome 的一路**，看小红书实帖（模板见下） |
| `logistics-weather` | 天气与雨天方案、各段地铁 vs 打车、节假日限流/延长运营、乘车码、打车上车点、车站进站/检票口/寄存、当年节假日预约名单 |

每个 prompt 结尾都要求：「最后给出你推荐的时间线 + 每段 Plan B」，并要求附来源和年份。

### 小红书浏览器那一路的提示词模板
```
【你的特殊任务：用浏览器看小红书真实帖子】这一条覆盖「不要用 Chrome」的约束——只有你可以用 Chrome。用户已在自己的 Chrome 登录小红书网页版。
操作规范（必须遵守）：
- 先用 ToolSearch 一次性加载：select:mcp__claude-in-chrome__tabs_context_mcp,mcp__claude-in-chrome__tabs_create_mcp,mcp__claude-in-chrome__navigate,mcp__claude-in-chrome__get_page_text,mcp__claude-in-chrome__find,mcp__claude-in-chrome__computer,mcp__claude-in-chrome__javascript_tool,mcp__claude-in-chrome__tabs_close_mcp
- 先调 tabs_context_mcp，然后新建自己的标签页，不动用户已有标签页；结束时关闭自己的标签页。
- 搜索用 https://www.xiaohongshu.com/search_result?keyword=<关键词>；笔记要在页面内点击打开（链接带 xsec_token，不要自己拼接，也不要在输出里写 token）。
- 只读：不点赞、不收藏、不关注、不评论、不私信。遇到验证码/滑块/登录墙立刻停止，不要尝试破解，把已拿到的信息返回并说明卡在哪。
- 单个 JS 循环不超过 30 秒，整体约 25 次页面操作以内。
要搜的关键词：<城市> <节日> 两天一夜 / <热门景点> 预约 / <夜游点> 人多 / <城市> 本地人 美食 / <城市> 避雷 / ……
每个关键词挑 2–3 篇高赞、近一年的笔记，提炼：排队/人流时间、预约技巧（放票时间点）、踩坑、推荐与避雷的店（店名+理由）、路线建议。注明来源笔记（标题+作者昵称+日期，不写 URL token）。
注意评论区回「私我」「能代约」的多半是黄牛，单独提醒。
```

## 3. 运行

```
Workflow({ scriptPath: "/Users/<你>/.claude/skills/trip-planner/scripts/research_workflow.js",
           args: { today: "YYYY-MM-DD", ctx: "...", topics: [...], extra_rules: "可选" } })
```
- 上次 7 路调研约 1.5–2 小时、合成约 30 分钟。跑的期间先去做不依赖结果的事：住宿、准备地图脚本、核对车次。
- 失败/中断：用返回的 `resumeFromRunId` 续跑，已完成的 agent 会直接用缓存。查结果看 `<transcriptDir>/journal.jsonl`（每个 agent 的返回值都在里面）。

## 4. 跑完怎么收

1. `plan` 存成 `<行程目录>/plan.json`；`research` 各路原文存成 `research_<key>.md`，后面答疑、改计划时要翻。
2. 逐条处理 `issues`：high 必改，medium 看情况，改完在聊天里列出改了什么。
3. 自己核对最要命的 2–3 条事实（WebFetch 打开原文）：热门景点放票/预约规则、节假日预约或禁车范围、返程车站相关。核对过的在 sources 里注明「已核对原文」。
4. 补齐 plan.json 里给页面用的字段：`kicker`、`trip_cards`（去程/住/回程三张卡）、每天的 `route`、酒店点加 `pin: true` 和推算坐标（OSM 一般查不到具体酒店：用最近两个地铁站的坐标按距离插值）。
