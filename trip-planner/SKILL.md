# 旅行规划：从「想出去玩」到「出发前一晚」

这套流程来自一次完整实战（2026 国庆杭州→南京一晚两天）。用户真正需要的不是一篇攻略，而是：**到了当地每一刻都知道下一步去哪、用哪张票、出了意外换什么**。所以产出的核心是「主线 + 替代方案 + 票在哪个 App」，而不是景点介绍。

## 0. 先记住节奏原则（实战教训）

上一次每天排了 8–10 个点、步行 12–15km，结果累到把科举博物馆、中山陵、美龄宫都砍了。所以：
- **每天 3–4 个核心点**，总步行尽量 ≤10km，中间留歇脚/回酒店的空档；
- 「可去可不去」的点放进替代方案或备选，不要塞主线；
- **主线不能依赖大概率约不到的东西**。热门景点（如中山陵）一般提前 7 天定点放票，临近出发只能刷回流票——这类做成「刷到再加」的可选项；
- 返程车次是硬约束：倒推出「最晚几点必须往车站走」，节假日留 ≥45 分钟进站余量。

## 1. 收集信息（一次问完，能默认的就默认）

需要：目的地（没定就先帮选）、日期、住几晚、几个人、出发城市、预算、偏好（默认美食 + 人文）、住宿偏好（默认性价比 + 位置，地铁/打车一半一半都行）。缺的一次性问，别一条条追问。本机时区可能不是北京，日期用 `TZ=Asia/Shanghai date` 算。

**没定目的地**：给 2–3 个候选，对比高铁时长、美食、人文、节假日人流，给推荐和理由，用户拍板再往下。

## 2. 先定交通，再排行程

- 用 12306 实时余票查车次和票价（`train-ticket-watch` skill 里的 12306-mcp；`get-tickets` 返回的 `start_date` 是始发站日期，别误读）。
- 热门日子没票：用 `train-ticket-watch` skill 后台盯票，有票按「**HH:MM 发车**」格式立刻报。
- 记下最终车次、车厢、座位、检票口——这些是后面一切时间的锚点。提醒用户：改签只能一次。

## 3. 住宿

读 `references/hotel-search.md`。要点：查**实际入住日期**的价格（节假日价格和平时差很多）、优先国内平台（携程/飞猪）看券后价、用户自己扫码登录（不要替用户输密码，遇到验证码就停）、看小红书/知乎/App 差评、确认**能寄存行李**和**免费取消截止时间**。订完让用户发订单截图，核对店名分店、日期、晚数。

## 4. 多 agent 调研 + 合成计划

用户说「多起几个 agent」「跑 workflow」「去小红书知乎找经验」时，或者行程 ≥1 晚、节假日出行时，用 Workflow 跑 `scripts/research_workflow.js`（调用本 skill 即视为用户同意跑多 agent 工作流）。怎么拆调研方向、`ctx` 写什么、小红书浏览器那一路的提示词模板、跑完怎么处理，见 `references/research-workflow.md`。

```
Workflow({ scriptPath: "~/.claude/skills/trip-planner/scripts/research_workflow.js",
           args: { today, ctx, topics: [{key, prompt}, ...], extra_rules } })
```
- 跑的时候告诉用户大概要多久（上次 7 路调研 + 合成约 2.5 小时），同时你去准备住宿/交通或地图素材。
- 结果是 `{plan, issues, research}`：把 `plan` 存成 `<行程目录>/plan.json`，逐条处理 `issues`（high 必改），再**亲自核对最要命的 2–3 条事实**（热门景点预约规则、节假日禁车/预约范围、返程相关）——用 WebFetch 打开官方或本地宝原文，不要只信 agent。
- 行程目录建议：`~/Documents/旅行计划/<YYYY-MM>-<城市>/`。plan.json 字段见 `references/plan-schema.md`。

## 5. 逐个过预约，并审核截图

读 `references/bookings.md`。用户最喜欢的节奏是「一个一个来」：每次只讲一项——**在哪个 App/小程序、日期、时段、张数、价格、约不到怎么办**，用户办完说「下一个」再讲下一项。用户发订单截图时逐张核对（日期、时段、人数、**午餐还是晚餐**、是否「待商家确认」、是否随时退、是不是两人共用一个码）。截图里的身份证号、手机号不要复述，并提醒用户别外发。

计划随预约结果变（约不到、只剩 17:30 的位）就及时调整主线和时间，并同步到所有交付物。

## 6. 交付物

用户要的是**到时候不用翻网页**。按这个顺序给（细节见 `references/deliverables.md`）：

1. **网页 + 地图**（Artifact）：
   ```bash
   S=~/.claude/skills/trip-planner/scripts; T=<行程目录>
   python3 $S/geocode_points.py $T <城市>      # map_points → GCJ-02 坐标
   python3 $S/fetch_tiles.py $T                 # 高德瓦片 → site/tiles/
   python3 $S/build_page.py $T                  # → site/index.html
   ```
   发布时 `file_path=$T/site/index.html`，`root=$T/site`，`files` 列出 `tiles/**/*.json` 全部文件。发布前用本地预览检查一次地图（本地预览要自己补 `<meta charset>`）。
2. **截图版流程**：直接在聊天里给，按天分块，每步「**时间 + 做什么**」一行、「🎫 用哪张票（哪个 App）」一行，末尾附「票在哪个 App」清单。这是用户在路上最常看的东西。
3. **离线单文件 + 路线总览图**（发微信/存手机）：`<有 Pillow 的 python> $S/build_offline.py $T` → `$T/offline/`。复制到 `~/Downloads` 并 `open -R`。
4. **给手机 Claude 的随身计划**：`python3 $S/make_phone_md.py $T "返程硬约束一句话"` → `$T/offline/plan.md`。告诉用户在手机 Claude 新对话里上传它（或贴链接），之后一直用这个对话语音问。
5. **（可选）放到用户自己的服务器**，让 iPhone Safari/微信/手机 Claude 直接打开：`$S/host/deploy.sh <ssh-host> $T <下线日期>`。这是对外发布，**必须先问用户**，并说明拿到链接的人都能看、到期自动下线。

## 7. 天气、穿衣和装备

读 `references/weather-packing.md`。定行程时看一眼大趋势（大雨那天把户外点和室内备选对调），**出发前一天必查**：
```bash
python3 $S/weather.py <城市> <开始> <结束> --spots <要去的山/湖/景区> --up <山比市区高多少米>
```
脚本同时给中国天气网（含景区单独预报）和 Open-Meteo（体感温度、哪几个小时下雨、阵风、紫外线、湿度），并按规则给出建议。你要做的是结合行程判断：
- **穿什么**：按出门活动时段（7–22 点）的体感温度，早晚和中午分开说；山上每高 100m 冷 0.6℃，湖边、城墙、坐船、夜游风大，要多一层。
- **伞还是雨衣**：城市里小雨带折叠伞；风大、爬山、坐船、雨大要加一次性雨衣、防水防滑鞋和备用袜子。
- **雨落在哪一段行程**：直接对照时间说出来，必要时调换室内外的顺序。
- 结论写进 plan.json 的 `packing` 和每天的 `weather`，再重新生成交付物；预报和上次比有变化要明确告诉用户。

另外把「待确认」的预约（餐厅商家确认短信、回流票时间点）列成当天的闹钟提醒。

## 8. 预算

分两块算：**已付**（按用户订单截图逐项，车票用 12306 查准确票价）+ **路上估算**（现场门票、市内交通、每餐、伴手礼），再列可选项（画舫之类）。给人均和总价区间。

## 9. 行程后

用户回来说「有几个地方没去」时：提醒去订单里退没用的票（「随时退」「过期退」的规则不同），并把这次的节奏教训记进记忆，下次排得更松。

## 常见坑（都踩过）

- **订座餐段**：餐厅订座可能默认成午餐（订成了 11:00），提交前看清「午餐/晚餐」和具体时间；「待商家确认」要等短信。
- **热门景点放票**：中山陵这类提前 7 天、每天 16:00 放票，当天还会投放退改名额；预约范围可能从广场就开始，没约到连门口都进不去。
- **节假日景区预约/禁车**：如夫子庙国庆 14:00–22:00 核心区要预约、周边禁车，打车只能在外围上下车。
- **Workflow 核查步骤**：不要让核查 agent 重写整份计划 JSON（几万字长时间无输出会被判卡死），只要问题清单——脚本已经这样做了。
- **WebSearch 有会话额度**：调研 agent 会用掉很多，主线程后面要查东西时改用 WebFetch/curl。
- **地图**：高德瓦片是 GCJ-02，OSM/Nominatim 是 WGS84，要转换；自定义 GridLayer 必须设 maxZoom，否则高清层被低清层盖住发糊；Artifact CSP 不让外链图片，所以瓦片随页发布。
- **离线版**：去掉 Google Fonts（国内会卡渲染）；iPhone 的微信/文件预览可能不跑脚本，所以内嵌了静态路线图兜底。
- **Chrome 自动化**：用户自己扫码登录；不碰验证码；小红书笔记要在页面内点开（链接带 xsec_token），不要拼接或输出 token；只读，不点赞评论。
